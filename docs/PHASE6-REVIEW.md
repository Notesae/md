- 本次独立重跑 12 项迁移核心用例，覆盖目标损坏、归属改变、首次未确认回滚、源保留、复制恢复与残留重试；全部通过。它们不能证明真实 WebView 会话释放、选择器或实际迁移 UI 已通过。
- 启动探针内的 `readyAtUnixMs` 在进入 `app_ready` 时采样，文件在健康提交后才出现。现有启动数字对应界面恢复点；如要统计“健康记录持久化完成”的耗时，应另记提交完成时刻，不能把这两种时刻混为一谈。

## 后续验收步骤与判定

1. **完整原生维护**：用 release 程序运行 `node tests/native-maintenance.mjs <release-exe>`。在选择器选 `PICKER_PARENT` 打印的父目录。保留本次 UUID 报告；要求 `mode=full`、`result=passed`，两项真实维护与七项故障恢复均有当前记录，并核对二进制 SHA、原文哈希、目标实际 WebView 文件、源删除与重启恢复。只通过第一项或 recovery-only 均不得勾选完整验收。
2. **性能与内存**：保持 SPEC 的样本数及预算，按 `docs/PHASE6-WINDOWS.md` 重跑；补充固定静置窗口内的进程组内存时间序列与全过程峰值，明确稳定判据，并在 100 次切换后比较趋势。保留全部样本，不以手动 GC、清工作集或取最低点换取 250MiB 通过。冷热缓存、系统重启与屏幕刷新条件分别记录。
3. **安装与首次启动**：使用不存在或为空、无重解析点的新 WorkRoot 重跑安装四条路径。另在干净用户环境中，不设置 `MD_BOOTSTRAP_DIR`，验证取消选择退出、选择非系统盘、正常读取与状态保存；记录真实默认引导目录和所选数据根的变化。
4. **系统盘写入**：Process Monitor 只导出本次阅读器及其 WebView 子进程的 PID 组。CSV 保留进程名、操作、路径、结果；覆盖首次启动、普通阅读、设置修改、异常退出和迁移等场景。用修复后的 `disk-audit.mjs --capture` 检查未知位置及引导单份 16KiB / 总计 64KiB 预算；对 CreateFile 的打开/创建区别及系统维护写入人工解释，不扩大允许根来掩盖结果。
